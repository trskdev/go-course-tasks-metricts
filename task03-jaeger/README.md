# task03. Трейсинг через OpenTelemetry → Jaeger

Метрики ты уже умеешь. Но метрика говорит "p95 вырос с 200 до 800ms" - а ты не знаешь, **где именно** тормозит. В базе? В походе за пользователем? В сериализации?

Трейсинг отвечает на "где". Один пришедший запрос = один **trace** = дерево **спанов**. Каждый спан - это одна операция внутри запроса (зашёл в handler, сходил в БД, вернул ответ). У спана есть длительность и родитель. В итоге ты видишь что-то вроде:

```
HTTP GET /order/42                    180ms
├── validateInput                       2ms
├── callDB                            150ms   ← вот оно
│   └── SELECT * FROM orders ...      148ms
└── writeResponse                       5ms
```

В этой задаче ты инструментируешь Go-сервис OpenTelemetry-ем и увидишь такую картинку в Jaeger UI.

---

## Почему OpenTelemetry, а не `jaeger-client-go`

`jaeger-client-go` **deprecated** с 2022-го. Команда Jaeger сама перешла на OpenTelemetry - это единый стандарт для всего observability-мира (Jaeger, Datadog, Honeycomb, Tempo, все дружат).

OTel разделяется на две части, и это важно:
- **API** (`go.opentelemetry.io/otel`) - то, что пишет бизнес-код: "начни спан", "закончи спан". Не знает и не должен знать, куда спаны идут.
- **SDK** (`go.opentelemetry.io/otel/sdk/trace`) - то, что настраивается в `main()`: куда слать, сколько сэмплить, как батчить.

Зачем такое разделение: завтра ты решишь переехать с Jaeger на Datadog - правишь только `main()`, бизнес-код не трогаешь.

---

## Словарь

| Термин | Что это |
|--------|---------|
| **Trace** | Всё дерево одного запроса. Имеет `trace_id` (128-битный id) - по нему можно найти конкретный запрос в Jaeger. |
| **Span** | Узел в дереве - одна операция. Имеет `span_id`, `parent_span_id`, имя, длительность, атрибуты. |
| **Context propagation** | Магия, благодаря которой `trace_id` передаётся между сервисами. По HTTP - через заголовок `traceparent` (стандарт W3C). |
| **Sampler** | Решает: этот trace сохраняем или выбрасываем? 100% в проде слишком дорого - обычно 1-10%. |
| **Exporter** | Отправляет готовые спаны в коллектор. У нас - по OTLP на Jaeger, порт 4318. |

---

## Что делаешь

1. В `main()` настраиваешь `TracerProvider` - скелет трейсинга. Туда втыкается exporter, resource с именем сервиса, sampler.
2. Оборачиваешь HTTP-мультиплексор в `otelhttp.NewHandler` - он на каждый входящий запрос автоматически создаёт корневой спан.
3. В хендлере создаёшь дочерние спаны: `validateInput` (валидация) и `callDB` (имитация запроса в БД).
4. Добавляешь атрибуты (`order.id`, `db.system` и т.д.) - они потом ищутся в UI.
5. В ~20% случаев помечаешь спан ошибкой - чтобы в UI было что-то красное.

Подсказки - в `// TODO:` в `main.go`.

## Запуск

> **Примечание:** в этой задаче мы изучаем только трейсинг, поэтому Prometheus
> не настроен на скрейп task03 (он слушает `:8082`, а конфиг Prometheus покрывает
> `:8081` для task01). Метрики можно посмотреть руками через `curl localhost:8082/metrics`,
> но в Prometheus UI они не появятся — это нормально.

```bash
# Из корня - поднимаем Jaeger
docker compose up -d jaeger

# В этой папке
go mod tidy
go run main.go

# В другом терминале - стучимся в сервис
curl localhost:8082/order/42
hey -z 30s -c 5 http://localhost:8082/order/42
```

Открой Jaeger UI - http://localhost:16686:
1. В дропдауне **Service** выбери `task03-jaeger`.
2. Жмёшь **Find Traces**.
3. Кликаешь по любому trace - откроется waterfall с тремя спанами.

Если что-то не появляется:
- Проверь, что сервис реально пишет в `:4318` (`curl -v localhost:4318/v1/traces` - должен отдать что-то, а не connection refused).
- Проверь, что в main.go вызывается `shutdown(ctx)` - без него батчер не успевает слить буфер.

## Что покрутить

### Сэмплинг

Прямо сейчас `sdktrace.AlwaysSample()` - сохраняется 100% трейсов. В проде так не делают (дорого по storage и bandwidth).

Замени на:
```go
sdktrace.TraceIDRatioBased(0.1)  // 10%
```

Запусти нагрузку на 1000 запросов, потом посчитай в Jaeger: должно быть около 100 трейсов. Обрати внимание - **либо весь trace, либо никакого**. Решение о сэмплинге принимается один раз на корневом сервисе и распространяется по цепочке.

### Атрибуты

Добавь больше атрибутов в `validateInput`:
```go
span.SetAttributes(
    attribute.String("http.method", r.Method),
    attribute.Int("input.length", len(id)),
)
```

В Jaeger открой этот спан и посмотри раздел **Tags**. По ним можно потом искать: "все трейсы, где `input.length > 10`".

### События (логи внутри спана)

Кроме атрибутов у спана есть события - это фактически структурированные логи, привязанные к моменту времени в спане:
```go
span.AddEvent("cache miss", trace.WithAttributes(attribute.String("key", id)))
```

В UI появятся на таймлайне внутри спана.

### Ошибки

Правильный способ пометить спан сломанным - два вызова:
```go
span.SetStatus(codes.Error, err.Error())  // красит спан в красное
span.RecordError(err)                      // добавляет событие с типом/сообщением/стеком
```

Отдельный только SetStatus - спан красный, но нет деталей. Отдельный только RecordError - детали есть, но на глаз спан выглядит ок. Делай оба.

## Как `traceparent` работает между сервисами

Забегая вперёд на task04: когда сервис А делает HTTP-вызов в сервис Б, OTel автоматически добавляет в заголовки:
```
traceparent: 00-<trace_id>-<parent_span_id>-01
```

Сервис Б, если он обёрнут в `otelhttp.NewHandler`, распарсит этот заголовок и создаст свой спан с тем же `trace_id`. В Jaeger оба сервиса окажутся в одном trace.

Если А забыл про инструментированный клиент или Б забыл про `otelhttp.NewHandler` - связь порвётся, будет два отдельных trace.
